### E. Observations on customer spending and data generator

All top spenders have almost the exact same number of orders (~940 to 1,030) and their spending is clustered very tightly between 946k € and 991k €. 

Looking at `ecommerce/dataset_generator.py`, customer names are generated by randomly combining 32 first names and 33 last names:
$$32 \times 33 = 1,056 \text{ unique people}$$

Since 1,000,000 orders are generated using uniform random selection, every customer gets picked roughly:
$$\frac{1,000,000}{1,056} \approx 947 \text{ times}$$

Because prices and quantities are also picked randomly with uniform bounds, everything averages out over ~1,000 orders. In a real e-commerce business, spending follows an 80/20 Pareto rule where a small percentage of customers account for most of the sales, whereas this synthetic dataset is unnaturally uniform.

## Activity 2.2 — Self-Join Analysis

### Step 1 — Measuring growth

Created the test tables:
```sql
CREATE TABLE people_50k  AS SELECT * FROM people_big WHERE id <= 50000;
CREATE TABLE people_100k AS SELECT * FROM people_big WHERE id <= 100000;
CREATE TABLE people_200k AS SELECT * FROM people_big WHERE id <= 200000;
```

Running the self-join:
```sql
SELECT COUNT(*)
FROM people_X p1
JOIN people_X p2 ON p1.country = p2.country;
```

**Measurements:**

| rows in table | join result (`COUNT(*)`) | time |
|---|---|---|
| 50 000 | 27,501,822 | ~3.5 s |
| 100 000 | 109,946,508 | ~13 s |
| 200 000 | 439,395,606 | ~52 s |

**Growth analysis:**
- Every time the row count doubles ($50\text{k} \to 100\text{k}$, and $100\text{k} \to 200\text{k}$), both the result size and the runtime grow by roughly **4x** ($2^2$).
- This is quadratic growth ($O(N^2)$) because everyone in country X joins with everyone else in country X ($k \times k = k^2$).

**Prediction for `people_big` (1,000,000 rows):**
- Scaling from 200k to 1M is a $5\times$ increase in rows.
- The result size will grow by $5^2 = 25\times$:
  $$439,395,606 \times 25 \approx \mathbf{10.98 \text{ billion pairs}}$$
- The runtime will also increase by ~25x, meaning on a single CPU core it will take **over 20 minutes**.

---

### Step 2 — Does an index help?

```sql
CREATE INDEX idx_country ON people_100k(country);
ANALYZE people_100k;
```

**Observation:**
No, the index does not help at all. The query still took around 13 seconds.

**Why?**
Checking `EXPLAIN ANALYZE`, Postgres ignores the index and still runs a Hash Join. An index is useful when filtering for a small fraction of rows (like `WHERE country = 'Austria'`), but in this query every single row is joined, producing ~110 million matches. Traversing an index 100,000 times for ~110 million pairs would require huge random I/O, which is actually slower than scanning the table sequentially. The bottleneck is generating and counting 110M matches in memory/CPU, not locating the rows.

---

### Step 3 — Query Rewrite (no join)

If country $c$ has $k$ rows, joining them produces $k \times k = k^2$ pairs. So we can just count how many people live in each country, square that count, and sum them up:

```sql
SELECT SUM(cnt * cnt)
FROM (
    SELECT country, COUNT(*)::BIGINT AS cnt
    FROM people_big
    GROUP BY country
) sub;
```

**Verification:**
- On `people_100k`: returns **109,946,508** in **~20 ms** (was ~13 s).
- On `people_big` (1M): returns **10,983,941,260** in **~0.25 s** (predicted >20 min).

This rewrite drops complexity from $O(N^2)$ down to $O(N)$.

### Step 4 — Written Discussion

#### 1. Hardware and index limitations vs query rewrite
Step 3 shows that fixing an $O(N^2)$ algorithm is far more effective than throwing hardware or indexes at it. If an algorithm is quadratic, doubling your CPU only buys you a 2x speedup at best, while doubling your data quadruples the workload. Adding indexes also cannot help when a query inherently generates hundreds of millions of cartesian combinations. Changing the query logic to $O(N)$ solved the bottleneck instantly with zero infrastructure cost.

#### 2. What if the business actually needs the pairs themselves?
If we need the actual pairs and not just the count, 1M rows will produce ~11 billion rows. That is roughly 1 Terabyte of data. A single Postgres instance will run out of memory or disk space and time out.
- A distributed cluster (like Apache Spark or Trino) handles this much better by partitioning by `country`. Since pairs only match within the same country, workers don't need to communicate with each other to compute their piece (embarrassingly parallel).
- In a real project, you should also question why a user needs 11 billion rows dumped, and add filters or pagination instead.

#### 3. Limits of an OLTP database for this workload in the cloud
- **Row-store I/O waste:** Postgres stores whole rows on 8KB disk pages. To scan just the `country` column for 1 million rows, it still has to read all the unneeded columns (`first_name`, `salary`, `department`), wasting disk and memory I/O. Columnar formats (like DuckDB or Parquet) only read the column needed.
- **Transactional interference:** Running heavy analytical queries on a live OLTP database locks CPU and memory, and long transactions prevent Postgres autovacuum from cleaning dead rows, causing table bloat and slowing down live customer transactions.
- **Architectural solution:** In production, decouple operational and analytical workloads. Use Change Data Capture (Debezium/Kafka) or ETL to stream changes from Postgres into an analytical store or data lakehouse, keeping the transactional database fast.
